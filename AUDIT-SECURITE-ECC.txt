1. DIAGNOSTIC — FAILES IDENTIFIÉES
================================================================================

BLOCKERS
--------
B1. Collections métier en signedIn() seul
    Fichier : firestore rulses.txt
    Impact  : tout compte Firebase Auth pouvait lire/écrire stock, ventes,
              mouvements, dépenses, etc. même sans profil actif valide.

B2. Self-réactivation isActive
    Fichier : firestore rulses.txt (match /users)
    Impact  : un utilisateur désactivé pouvait remettre isActive: true sur
              son propre document.

B3. Vente non atomique
    Fichier : js/index.js → processSaleOnline
    Impact  : stock + sale en transaction, puis sale_items / stock_movements
              hors transaction → risque vente orpheline / stock faux.

B4. Stats / Dashboard incluaient les ventes cancelled
    Fichiers : js/loader.js, js/render.js, js/stats.js
    Impact  : CA et bénéfices gonflés après annulation de vente.

B5. Signup role incohérent (corrigé puis rétabli selon choix métier)
    Voir section 3 — rôle "user" conservé volontairement pour la sécurité.


HIGH RISKS
----------
H1. stock_current jamais recalculé depuis stock_movements (dérive possible)
H2. Achat non atomique (purchase + items avant stock/mouvement)
H3. Offline sync : double exécution multi-onglets possible
H4. CSP absente sur pages critiques (index, login, vendus, etc.)
H5. writeLog avalait les erreurs sans trace
H6. innerHTML dans settings (formulaire config)
H7. Dépenses créées sans status: "active"

2. CORRECTIONS APPLIQUÉES
================================================================================

A. FIRESTORE RULES (firestore rulses.txt)
-----------------------------------------
- Écritures métier : isActiveMember() (auth + user actif + rôle admin|seller)
- Lectures métier : signedIn() (conservé pour perf / compat)
- sale_items, stock_movements, purchase_items, batch_movements, logs :
  CREATE ONLY (update/delete refusés) — aligné Collections.md
- users update self : role, userId, isActive immuables (anti self-réactivation)
- isAdmin() exige aussi isActive == true
- Création user signup : role forcé == "user" (voir section 3)

IMPORTANT — DÉPLOIEMENT MANUEL OBLIGATOIRE :
  Firebase Console → Firestore → Règles → coller firestore rulses.txt → Publier
  Sans cette étape, les rules durcies restent INACTIVES en production.


B. SIGNUP / AUTH (sécurité par rôle)
------------------------------------
- js/signup.js     → role: "user" à l’inscription
- js/auth-flow.js  → role: "user" (Google / ensureFirestoreUser)
- Règles          → create users uniquement avec role == "user"

Effet sécurité :
  Nouveau compte = "user" → PAS d’écriture métier (isActiveMember refuse).
  Un admin doit promouvoir en "seller" ou "admin" pour ouvrir l’accès écriture.


C. STATS / DASHBOARD — filtre cancelled
---------------------------------------
- js/loader.js  : sales filtrées status !== "cancelled" avant KPI
- js/render.js  : activeSales() + bénéfice lié aux saleIds actifs
- js/stats.js   : buildPdfPayload() ignore les ventes cancelled

Alignement avec vendeurs.js / chart.js déjà corrects.


D. VENTE ATOMIQUE (js/index.js)
-------------------------------
processSaleOnline : UNE seule runTransaction contenant :
  - décrément stock_current
  - create sales
  - create sale_items
  - create stock_movements OUT
  - create debts si paiement partial

Refresh expiration cache reste hors transaction (cache UI, non critique).


E. ACHAT ATOMIQUE (js/purchases.js)
-----------------------------------
processPurchaseOnline : UNE seule runTransaction contenant :
  - create purchases
  - create purchase_items
  - update stock_current (+ price_buy éventuel)
  - create stock_movements IN


F. OFFLINE SYNC (js/offline.js)
-------------------------------
- Verrou multi-onglets : navigator.locks + fallback localStorage TTL
- Actions au-delà de 5 retries : abandonnées avec toast visible
- isSyncing par onglet conservé en complément

3. RÔLE "user" AU SIGNUP — CHOIX SÉCURITÉ CONFIRMÉ
================================================================================

Ce n’est PAS un bug. C’est volontaire :

  Inscription  → role: "user"
  Accès métier écriture → seulement après promotion admin → seller | admin

Schéma rôles :
  user   = compte créé, en attente / restreint
  seller = vendeur opérationnel
  admin  = administration

Ne PAS remettre role: "seller" automatiquement au signup.
